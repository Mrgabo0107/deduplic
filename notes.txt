Buen momento para pensarlo — hacerlo durante el refactor (no después) es lo correcto porque estás tocando cada función de todas formas. Aquí van los frentes que suelen escapársele a la gente:

## 1. Docstrings: hazlo por capa, no parejo en todo

No toda función necesita el mismo nivel de detalle:

- **API pública de `core`** (lo que expones en `__init__.py`): docstring completo — qué hace, parámetros con tipo y significado, qué retorna, qué excepciones lanza, y si hay efectos secundarios (escribe archivos, modifica estado). Ejemplo mínimo aceptable:
  ```python
  def deduplic_init(path: Path, config: DedupConfig) -> DedupState:
      """Inicializa el estado de deduplicación para un corpus.

      Args:
          path: Ruta al archivo JSON con los registros de entrada.
          config: Configuración de umbrales y método de comparación.

      Returns:
          Estado inicial serializable, listo para pasar a `deduplic_cluster`.

      Raises:
          FileNotFoundError: Si `path` no existe.
          InvalidCorpusError: Si el JSON no cumple el esquema esperado.
      """
  ```
- **Funciones internas/privadas** (`_helper`, cosas en `core/methods/utils.py`): un docstring de una línea basta, o incluso solo un comentario si el nombre ya es autoexplicativo.
- **`cli_cmds/cmd_*.py`**: no necesita docstring de función — necesita que el `--help` de argparse esté bien escrito (`description=`, `help=` en cada argumento). Esa es su "documentación".

## 2. Lo que casi siempre se escapa (checklist específico para tu caso)

- **Excepciones personalizadas**: documenta en un solo lugar (puede ser un docstring en el módulo donde las defines, o una sección del README) cuándo se lanza cada una — `DeduplicationError`, `InvalidCorpusError`, etc. Si no lo haces, quien consuma la librería solo descubre las excepciones leyendo el código o con prueba y error.
- **El contrato de los "métodos" de deduplicación** (`keep_first`, `keep_largest`, etc.): como son intercambiables, documenta explícitamente la interfaz común que todos cumplen (firma esperada, qué reciben, qué devuelven) en un solo lugar — probablemente en `core/methods/__init__.py` o un docstring de módulo ahí. Así cuando agregues un método nuevo, sabes exactamente qué contrato cumplir.
- **Formato de los archivos de estado/JSON que persistes** (`state.json`, merges guardados): esto se te puede olvidar fácilmente porque "ya sabes cómo es", pero seis meses después no. Documenta el esquema (aunque sea informal, un ejemplo de JSON comentado) en algún lado — idealmente cerca de `draft_io.py` o `merge_manager.py`.
- **Variables de entorno / `config.py`**: cada variable en `.env.example` con un comentario de qué hace y su default.
- **Efectos secundarios no obvios**: si alguna función de `core` escribe a disco, modifica un archivo de estado global, o depende de orden de llamada (ej. "hay que llamar `init` antes que `cluster`"), eso va en el docstring como advertencia explícita, no se asume que el usuario lo va a intuir.

## 3. Nivel de proyecto (no por función)

- **README.md**: instalación (`pip install deduplic[gui]` vs solo core), quickstart de 5-10 líneas de código mostrando el flujo típico (`init` → `cluster` → revisar → `commit`), y cómo usar los comandos de consola.
- **CHANGELOG.md**: aunque sea uso interno por ahora, empieza a llevarlo desde ya — durante un refactor grande es el mejor momento porque si no, seis meses después nadie recuerda qué cambió y por qué.
- **Un ADR informal o sección "Decisiones de diseño"**: cosas como "por qué core no puede importar de cli_cmds" o "por qué streamlit es opcional" — esto es justo lo que hemos discutido en este chat. Vale la pena dejarlo escrito una vez, en vez de tener que reexplicártelo (o explicárselo a otra persona) después.

## 4. Type hints como documentación viva

Esto no reemplaza el docstring, pero reduce mucho lo que tienes que escribir a mano: si `core` está bien tipado (`Path`, `DedupConfig`, `list[Record]`, etc.), herramientas como `mkdocs` + `mkdocstrings` o incluso solo el autocompletado del editor generan buena parte de la documentación de forma automática a partir del código. Vale la pena tipar bien *antes* de escribir docstrings extensos, para no duplicar información entre el tipo y el texto.

## 5. Momento práctico de hacerlo

Como ya estás en Fase B (moviendo lógica de `cli_cmds` a `core`), el momento natural es: **cada vez que muevas/reescribas una función a `core`, escríbele el docstring completo en el mismo commit**, no lo dejes para después — es cuando tienes el contexto fresco de qué hace y qué asume.

Sobre tu pregunta: Python no da ningún mensaje amigable por defecto. Si alguien instala solo con pip install deduplic (sin [gui]) y ejecuta deduplic_gui, lo que va a ver es un traceback crudo tipo:

Traceback (most recent call last):
  File "/home/user/.venv/bin/deduplic_gui", line 8, in <module>
    sys.exit(run_gui())
  File ".../deduplic/cli_cmds/cmd_deduplic_launch_gui.py", line 3, in run_gui
    import streamlit as st
ModuleNotFoundError: No module named 'streamlit'

Esto es técnicamente correcto (el programa falla porque falta la dependencia), pero es una pésima experiencia — el usuario no tiene idea de que existe un extra [gui] a menos que lea tu documentación primero. Python no resuelve esto automáticamente; tienes que capturar el ImportError tú mismo y traducirlo a un mensaje accionable, exactamente el patrón que discutimos hace varios mensajes.

Así se ve implementado en cmd_deduplic_launch_gui.py:

python
"""Entry point for launching the Streamlit GUI."""

import sys


def run_gui() -> None:
    """Launches the Streamlit-based graphical interface.

    Requires the 'gui' extra to be installed. Prints an actionable message
    and exits with a non-zero status if streamlit is unavailable.
    """
    try:
        import streamlit  # noqa: F401 (import solo para verificar disponibilidad)
    except ImportError:
        print(
            "Error: la interfaz gráfica requiere dependencias adicionales.\n"
            "Instálalas con:\n\n"
            "    pip install deduplic[gui]\n",
            file=sys.stderr,
        )
        sys.exit(1)

    # A partir de aquí streamlit ya está disponible; lanza la app real
    from deduplic.streamlit_gui.app import main as streamlit_main
    streamlit_main()

Puntos clave de por qué se hace así:

El import streamlit va dentro de la función, no al inicio del módulo — así, el archivo cmd_deduplic_launch_gui.py se puede importar sin problema (por ejemplo, si algo más adelante hiciera from deduplic.cli_cmds import cmd_deduplic_launch_gui con otro propósito) incluso sin streamlit instalado. El costo de la dependencia solo se paga cuando alguien de verdad ejecuta run_gui().
sys.exit(1) — código de salida distinto de cero, correcto para un fallo de CLI (permite que scripts que llamen a tu comando detecten el error mediante $? o subprocess.returncode).
El mensaje va a stderr, no a stdout — convención estándar para errores en herramientas de consola, para que no se mezcle con salida "normal" del programa si alguien redirige la salida (deduplic_gui > log.txt).
Nota el from deduplic.streamlit_gui.app import main después del chequeo — así, si por algún motivo la importación real de tu módulo de GUI (no solo streamlit) falla por otra razón, ese error sí se ve tal cual, sin que tu mensaje genérico lo enmascare.

Con este patrón: quien instale la librería completa (pip install deduplic[gui]) no nota ninguna diferencia; quien instale solo el core y por error/curiosidad ejecute deduplic_gui, recibe instrucción clara de qué hacer, en vez de un traceback que no dice nada sobre extras opcionales.
